# ADR 0002: Вход через OIDC

- Статус: принято; конфигурация провайдера через env заменена [ADR 0006](0006-oidc-settings.md)
- Дата: 2026-11-09

## Контекст

M4 добавляет вход через внешний OpenID Connect провайдер (Authentik, Keycloak, Authelia, Google, …), автосоздание пользователей и роли из claims. Нужно было решить, как связывать внешние аккаунты с локальными, когда обновлять роль, где хранить состояние незавершённого входа и сколько провайдеров поддерживать.

## Решение

- **Один провайдер.** Он настраивается через `ACKSY_OIDC_*` или секцию `oidc:` в YAML. В схеме внешний аккаунт хранится как пара `(issuer, subject)` в таблице `user_identities` (у пользователя их может быть несколько), так что добавить ещё провайдеры можно без миграции.
- **Нет автоматического связывания с существующими пользователями.** При входе пользователь ищется только по `(issuer, sub)`. Если идентичность неизвестна и `auto_create` включён, создаётся новый пользователь без пароля. Его username берётся из `username_claim`, затем из локальной части email, затем из имени. Если имя занято, добавляется суффикс `-2`, `-3`, … Связать существующего пользователя можно только явно: `acksy user link-oidc`. Иначе любой, кто заведёт в IdP логин `admin` или неподтверждённый email админа, получил бы его аккаунт.
- **Роль синхронизируется при каждом входе**, если задан `admin_values`. Значения `role_claim` (строка или список, по умолчанию `groups`) сравниваются точно: admin, если есть пересечение, иначе user. Последнего активного админа не понижаем: вход проходит с прежней ролью, в лог пишется предупреждение. Без `admin_values` роль из claims не берётся вообще (новые пользователи получают `user`), и ролями управляют в Acksy.
- **Протокол:** authorization code flow с PKCE (S256) и nonce. `go-oidc` проверяет подпись, issuer, audience и срок, а nonce проверяем сами, потому что `Verify` этого не делает. Claims, которых нет в ID token, дочитываются из UserInfo, если `sub` совпадает.
- **Состояние входа** (state, nonce, PKCE verifier, путь возврата) лежит в короткоживущей cookie `acksy_oidc`: `HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth/oidc`, 10 минут, одноразовая. Таблица не нужна, а несколько инстансов работают без общего секрета. Совпадение `state` с cookie привязывает callback к браузеру, начавшему вход.
- **Discovery ленивый.** Провайдер опрашивается при первом входе и повторно после ошибки, поэтому недоступный IdP не мешает серверу стартовать. Пользователь видит `/login?error=oidc_unavailable`.
- **Вход по паролю** остаётся по умолчанию. `disable_password_login` отключает `POST /auth/login` в сервисе (403) и прячет форму в UI. CLI продолжает работать.
- После входа выдаётся обычная login-сессия Acksy. Токены провайдера не хранятся, сессия не зависит от сессии в IdP.

## Последствия

- Если в IdP у пользователя сменится username, в Acksy это не отразится: связь держится на `sub`.
- Пользователь, отключённый в Acksy, не войдёт и через OIDC. А вот отключение в IdP не завершает уже выданные сессии Acksy, они живут до `ACKSY_SESSION_TTL`.
- RP-initiated logout (выход из IdP) и back-channel logout пока не сделаны.
- Ограничить вход группой можно на стороне IdP (политика приложения в Authentik или Keycloak). Отдельного allow-list в Acksy нет.
- Связывать и отвязывать идентичности админ может и из веб-интерфейса (Settings → Users), через `/api/v1/users/{id}/identities`. Правило «нет автоматического связывания» от этого не меняется: связь всегда создаёт админ.

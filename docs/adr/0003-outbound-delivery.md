# ADR 0003: Доставка наружу (Web Push, вебхуки), SSRF-защита

- Статус: принято
- Дата: 2026-11-09

## Контекст

M6 выводит уведомления за пределы Acksy: сначала Web Push в браузеры, затем исходящие вебхуки. Нужно было решить, как доставка встраивается в публикацию, не нарушая инвариант 3 (сначала коммит, потом fan-out), насколько надёжной она должна быть и как ходить на URL, которые присылают пользователи.

## Решение

- **Хук после коммита.** `service.Publish` после успешной транзакции передаёт записанные уведомления зарегистрированным `service.Notifier`. Это то же место, где события уходят в брокер. Передаются только уведомления, способные потревожить пользователя: непрочитанные, не в архиве, не отложенные и не истёкшие. Повтор по dedup поднимает уведомление (M3), поэтому push уходит снова.
- **Notifier не блокирует.** Реализация (`internal/delivery/webpush.Dispatcher`) кладёт работу в ограниченную очередь в памяти. Воркеры запускаются из `app`, а `Serve` дожидается их остановки. Направление зависимостей сохраняется: `delivery → service`. Сервис знает только интерфейс, `app` связывает их при старте.
- **Web Push — best effort.** Очередь не персистентная. Если она переполнена или процесс перезапустился, push пропадает: его ценность в моменте, а состояние клиент всё равно восстанавливает через API и `since=<seq>`. Ретраев нет, неудачи считаются на подписке (`failures`). Ответы 404/410 от push-сервиса удаляют подписку. Для вебхуков это не подойдёт, им нужна очередь в БД с ретраями (вторая часть M6).
- **Подписки** привязаны к пользователю и браузеру (`endpoint` UNIQUE). Повторная подписка с того же браузера под другим пользователем переносит запись. Управлять ими можно только из login-сессии. `endpoint` и ключи — секреты (по ним можно слать на устройство), поэтому API показывает только хост push-сервиса. У каждого устройства свой порог `min_priority`, по умолчанию 3. Не больше 20 устройств на пользователя.
- **Содержимое push:** заголовок и превью тела не длиннее 200 символов. Превью — это markdown, отрендеренный на сервере и очищенный до текста (`internal/markdown`, goldmark + bluemonday, инвариант 8). Payload шифруется до браузера (RFC 8291), push-сервис видит только размер и время. `Urgency` зависит от приоритета. `Topic` строится из хеша dedup-ключа, чтобы push-сервис схлопывал недоставленные повторы. TTL — 24 часа, но не дольше `expires_at`.
- **VAPID-ключи** генерируются при первом старте и хранятся в `instance_settings` одной JSON-записью: при одновременном старте нескольких инстансов пара не перемешается. Их можно задать через `ACKSY_VAPID_*`. Subject берётся из `ACKSY_VAPID_SUBJECT` или https-`BASE_URL`, без него Safari отклоняет push.
- **SSRF.** Запросы на пользовательские URL (push endpoint, позже вебхуки) идут через `internal/netguard`. Его dialer отказывается соединяться с приватными, loopback, link-local, CGNAT, NAT64 и прочими непубличными адресами. Проверка срабатывает на итоговый адрес в момент соединения, поэтому её не обходят ни DNS-ребиндинг, ни редиректы. Прокси из окружения игнорируются: прокси скрыл бы реальный адрес назначения.

- **Вебхуки надёжны**, в отличие от push. Доставки пишутся в `webhook_deliveries` **в транзакции публикации** (снапшот уведомления в JSON), поэтому существуют ровно тогда, когда существует уведомление. После коммита `Notifier` только будит воркер, а он ещё и опрашивает очередь каждые 5 секунд. Захват — портируемый условный `UPDATE … WHERE next_attempt_at <= now` с проверкой числа затронутых строк. `SKIP LOCKED` (только Postgres) не нужен, и несколько инстансов не шлют дубли. Доставка удаляется после 2xx. При временной ошибке переносится по расписанию (8 попыток), при постоянной ошибке или после последней попытки получает `failed_at` и позже удаляется уборщиком.
- **Подпись вебхуков:** HMAC-SHA256 от `<timestamp>.<body>`. Секрет хранится открытым (иначе нечем подписывать) и показывается только при создании и ротации. Discord и Slack кладут секрет в путь URL, поэтому API показывает URL только до хоста, а в ошибки и логи URL не попадает.
- **Вебхукам в LAN можно разрешить приватные адреса:** `ACKSY_WEBHOOK_ALLOW_PRIVATE`, по умолчанию выключено.

## Последствия

- Push может потеряться при рестарте или переполнении очереди. Это осознанный компромисс.
- Когда отложенное уведомление «просыпается», push не отправляется: для этого нужен планировщик. Уведомление просто появляется во входящих.
- Push-сервис на приватном адресе (например, свой autopush в LAN) использовать нельзя, пока не появится опция `AllowPrivate`.
- Каждая публикация с подходящими вебхуками добавляет строки в транзакцию. Для типичных объёмов это мелочь, а длинную очередь при недоступном получателе ограничивают ретраи и уборка.
